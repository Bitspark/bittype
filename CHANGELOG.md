# Changelog

## A declaration's definition is its entity's body in the Go and TypeScript analyses (13 November 2026)

The Go and the TypeScript analysis published, as the body of a declaration's entity, a reference to that entity itself, and related the definition to it by a fact of their own. The generation kernel opens a declaration at its body and reads no fact, so neither language could be a generation source. This is [#310](https://github.com/Bitspark/bittype/issues/310), from [decision O45 on #196](https://github.com/Bitspark/bittype/issues/196#issuecomment-6854327944), recorded as [bittype/ACX-013](docs/architecture-cases/0013-definition-behind-a-fact.md). The contribution contract and the kernel did not change.

- **Go.** The body of a captured type declaration or alias is the term of the type that its written right-hand side denotes: a `struct`, `slice` or `basic` expression, a Reference to another declaration (`type Temp Celsius`), or an Application (`type People = Page[Person]`). A type parameter, a predeclared type and a supplied declaration have no body. [The table](docs/native-semantics.md#go-bodies-and-declared-types) states every kind.
- **The type of a Go name is a fact.** Every entity of a type name carries one `declared-type` fact, `golang.DeclaredTypeRelation()`, whose term is the one that `underlying`, `alias-target`, `constraint`, `display` and `identical` hang on. `Model.DeclaredType(entity)` is new and reads it. `Lookup`, `LookupIn` and `Type.Parameters` read it and answer as before.
- **TypeScript.** The body of an alias is the term of its written right-hand side: a Reference (`type Alias = Text`), an Application (`type People = Page<Person>`) or the structural expression. The body of an interface without an `extends` clause is the `object` of its members. A type parameter has no body. `declared-type` was an entity fact before and stays the way to the type of a name. [The table](docs/native-semantics.md#typescript-bodies-and-declared-types) states every kind.
- **An interface with base types has an `extension` as its body** ([decision D2](https://github.com/Bitspark/bittype/issues/310#issuecomment-6857138520)): a provider expression whose data is `{"Bases": n}` and whose operands are the `n` base type terms as written, in written order, and then one `object` of the members that the interface declares itself. A base with type arguments is an Application. `semantics/typescript/go` publishes `ExtensionOperator()`, `ExtensionInfo` and the reader `Model.Extension(term)`. The declared type and the `properties` fact still give all members, inherited ones too. [The form](docs/native-semantics.md#the-extension-of-an-interface).
- **A right-hand side that the compiler reduces to another named type is a use of that type** ([decision D4](https://github.com/Bitspark/bittype/pull/315#issuecomment-6862246686)). The body of `type M = A & unknown`, `A | never`, `A & {}` or `Box<string> & unknown` is a Reference to `A`, or the Application, for a captured and for a supplied type alike. It is not the structure of `A`, which is the body of `A` alone.
- **`Model.Extension` reads the published form exactly** (decision D6): the encoding `typescript.JSONEncoding()`, the data as the bytes `{"Bases":n}`, each base a Reference or an Application.
- **`typescript.Model.DeclaredType(entity)`** reads the `declared-type` fact by entity, also for a property. `typescript.Profile` and `golang.Profile` are the profile names without the operation, and the profile strings are built from them.
- **The Go bridge sets bodies in a pass of their own** (decision D5), so a chain of 200 defined types is analysed as before. **What fits in the record budget changed:** every type name and every field carries one more fact. A chain of 129 defined types has 524 facts where it had 394, and a struct of 2,000 string fields 2,015 where it had 13, against a budget of 32,768 entities, terms and facts.
- **A field and a property have no body** ([decision D1](https://github.com/Bitspark/bittype/issues/310#issuecomment-6857138520)). The entity of a Go field and of a TypeScript property carries its type as the `declared-type` fact. `Type.Fields` and `Type.Properties` read the type from the operand of the struct or object term and answer as before. So `Body` has one meaning in both graphs: the written definition of a captured declaration.
- **Incompatible: both profiles have their second version.** `go1.25/captured-types-2/resolution-1` and `go1.25/captured-types-2/analysis-1`; `typescript-5.9.3/captured-types-2/resolution-1` and `typescript-5.9.3/captured-types-2/analysis-1`. A published member changed, so by the line drawn on #278 the strings changed. The TypeScript `helper` setting is `captured-types-2`, published as `typescript.HelperProfile`. A receipt of the earlier version is refused. The Go vocabulary publishes the profile's name without its operation as `golang.Profile`. The verification's native basis reads it, so `NativeBasis` is `go1.25/captured-types-2`, which a receiver that permits names by the constant takes without a change and one that spells the name must update.
- **Incompatible for a reader of a graph:** code that read `Entity.Body` of a Go or TypeScript graph as the type of a name, a field or a property reads the definition now, or nothing. Read the `declared-type` fact.
- **One reader for the one fact of a subject.** `semantics.Semantics[L].OnlyFact(subject, relation)` returns the term when exactly one fact is recorded. The Go readers use it. It gives a relation no meaning, and `Facts` is unchanged.
- **Tests.** One reader in a test file walks a graph as the kernel does (body, operands, reference targets, direct parameter bindings, no fact) and reaches, for Go and for TypeScript, every field, a reference to another declaration, a recursive declaration, a use of a generic declaration's parameter and an application paired with that parameter. Each was red on `main`. Further tests state the body and the declared type of each declaration kind and refuse a receipt of the earlier profile.
- **Rust was read and not run.** Its helper sets the body of a struct and an enum to a reference to, or an application of, the entity itself. That is recorded in the case as an open violation. It is corrected next under #310 in its own pull request ([decision D3](https://github.com/Bitspark/bittype/issues/310#issuecomment-6857138520)).

## One bounded writer for a child process's streams — 13 November 2026

Three packages each had a copy of the writer that collects a child process's stream against a bound: the Rust and the TypeScript compiler bridge, and the loader of the reporting tool. The loader's copy did not enforce its bound. This is [#299](https://github.com/Bitspark/bittype/issues/299) and [bittype/ACX-014](docs/architecture-cases/0014-bounded-process-writer.md). It corrects a violation of platform's rule [AC-11](https://github.com/Bitspark/platform/blob/main/docs/concepts/architectural-correctness.md#ac-11): "Per-language copies of that mechanism are forbidden", and "the size of a helper cannot justify language-specific ownership of an agnostic mechanism". The entry of #296 further down says "Two copies of the type stay". That decision was wrong, and this change takes it back. No contract, vocabulary or generated output changes.

- **One package, `internal/processoutput`.** A `Bound` is a number of bytes and the function that cancels the process. `Bound.Writer` returns a writer that draws on it, and writers of one bound share it. `Write` is the only method that takes bytes. A write that would pass the bound appends nothing, cancels the process once and returns `ErrBound`, and every later write of every writer of that bound is refused. The cancel function is called after the bound reports itself passed and outside the bound's lock, so it may ask the bound. `NewBound` refuses a missing cancel function, and a writer that no bound returned refuses every write. The package imports no package of the module.
- **Its place comes from the layout.** [The layout](LAYOUT.md#dependency-direction) has the role "Shared private helper" with the rule "A helper of no single language cannot conceal a language", and the [package boundaries](docs/package-boundaries.md#rules-to-enforce) list those helpers as entries of the foundation table. A tool already imports a shared helper under its own entry: `tools/horos-module/go` lists `internal/lex`.
- **The three callers keep what is theirs.** Each bridge gives each stream its own bound, 16 MiB for the output stream and 256 KiB (Rust) or 16 KiB (TypeScript) for the error stream, and returns `semantic.ErrLimit` and no output when one is passed. The loader gives the output streams and the error streams of its two Go commands one bound, `MaxMetadataBytes`, and fails with "Go command output exceeds N bytes". The three copies are deleted: `boundedBuffer` twice, and `outputBudget` with `boundedOutput`.
- **The loader's budget holds now.** Its writer embedded `bytes.Buffer`, so `os/exec` filled it through `ReadFrom` and the bounded `Write` was not called. This is the defect that #296 corrected in the two bridges. A load whose Go commands write more than the budget now fails, and the command is cancelled. On the workstation the Go commands of a load of this repository write 898,135 bytes, and the default budget is 64 MiB.
- **Two differences in behaviour, and no caller sees either.** The loader's copy kept the part of a refused write that still fitted. The one writer keeps nothing of a refused write, as the bridges' copies did. And `Bytes` returns nothing once its bound is passed, where the copies returned what they had collected: a stream with its end cut off must not read as a whole one. All three callers ask `Exceeded` first and return no output after a passed bound.
- **One fixture for the tests, `internal/processoutput/processoutputtest`.** The tests start a real child process, the test binary itself, that writes stated numbers of bytes and in some cases never exits by itself. #298 wrote that child and its harness once per bridge, and the first form of this change wrote them a third and a fourth time. The independent review measured 60 code lines identical in all four test files. The package holds the child, its description and the harness once, and the four test files use it. Each package keeps how its test binary knows that it is the child, what the output stream starts with, whether the child reads its input stream, and the call under test. The two bridge test files of #298 are edited for this: their cases, bounds and assertions are unchanged.
- **A false failure of those tests is corrected once, in the harness.** It waited for the first of two events, the child's connection and the return of the call, and failed when the return came first, which nothing in the test's process forbids. The review saw it in 1 to 10 of 100 runs on a loaded host, and the same lines were on `main` since #298. The harness keeps a return that comes first and awaits the connection after it. The process tests of the four packages then ran 300 times each with the default number of processors and 300 times each on one, 2400 runs, without a failure. The earlier test files, run after them under the same conditions, failed 5 of 300 runs of the writer's test and 1 of 100 of the loader's.
- **The architecture test** gains the entry of each of the two packages, with no import, and the import of the writer for each of its three importers. The writer is a helper of no single language in `foundationRules`. The fixture is used by tests only, so it is an entry of `oneOfAKindRules`: no foundation or kernel package can import it then, whatever its entry lists. `roleExtensions` names the writer for `internal/rustsem` and for `internal/typescriptsem`, and the entry of `tools/provider-matrix/report/go` lists it. Each of the three is checked for use by its own package, so a bridge or the loader that goes back to a writer of its own and drops the import fails `TestProductionArchitecture`. Only test files import the fixture, and the check reads no test file, so no importer has an allowance for it.
- **Tests.** `TestLoadBoundsGoCommandOutput` puts a copy of the test binary in the search path under the name `go` and lets it write exact numbers of bytes: the four streams of the two commands at the budget, one byte more on each of them, and a first command that passes the budget alone, each for a process that exits and for one that never exits by itself. `TestLoadFailsWhenTheGoCommandPassesTheBudget` loads a module with the Go command itself and a budget of sixteen bytes. Both fail on `main`: the loader read every oversized stream whole and cancelled nothing. The tests of `internal/processoutput` read the method set of its two types, run the writer against a real child process with one bound per stream and with one shared bound, give it a cancel function that asks the bound, which never returns when cancel runs inside the lock, and write to it from eight goroutines while a ninth reads the bound and the writers, and fail when no read fell between the writes. `TestHelperOutputBound` of both bridges passes with its cases and assertions unchanged. Of 65 mutants, 64 fail a test: 21 of the writer, 2 of the fixture, 12 of each bridge's use of the writer, 8 of the loader's use of it and 10 of the entries in the architecture test. The one that passes removes the lock from `Exceeded` and `Bytes`, which only the race detector can show.
- **The race detector runs these tests in the hosted job.** A new step of `.github/workflows/go.yml` runs the tests of `internal/processoutput` and of `tools/provider-matrix/report/go` under it. Before, it reached the writer only through two tests of the bridges, and never two writers of one bound.
- **Tests that went with the copies.** `TestBoundedBufferOnlyWrites` in both bridge packages, and the last lines of `TestCaptureLimitsAndOffsets` and `TestPrepareInvalidTextAndDeadline`, built a bridge's own type by its unexported fields. They are deleted, and the tests of the owner assert what they asserted. The first lines of the loader's `TestLoadBudgetsCancelCommandOutputAndRejectInvalidFlags` built the loader's own type. They are deleted, and the rest of that test is `TestLoadRejectsInvalidFlagsAndNegativeLimits`.
- **Unchanged output.** 159 values that the integration tests generate, format or place have the same SHA-256 on `main` and with this change.
- **Counts made again.** [Package boundaries](docs/package-boundaries.md#what-the-test-enforces-now) gives the tables of the architecture test as they are with this change: 32 entries in `foundationRules`, 13 in `oneOfAKindRules` and 14 in `roleExtensions`, of 131 production packages.

Not done:

- Other limits of the bridges and of the tool, which the work item leaves out. Among them is the wait of one or two seconds that a caller gives the copies of the streams after its process has exited.
- A copy that keeps the import is not seen by any test: a package that uses the shared writer for one stream and a writer of its own for another passes. Nothing fails either when a new package starts a process with its own bounded writer, or a test with its own child process. The layout says that it must not.
- The race detector does not run on the workstation. That it reports a read of the bound without the lock was reasoned and not run.
- `limitedText` in `tools/provider-matrix/report/go/details.go` embeds `strings.Builder`, so two of its methods pass its bound. The review saw it. It is no writer for a child process and gets its own issue.

## Design: models and operations, the root split and how it is carried out — 13 November 2026

The owner directed on 13 November 2026 that the repository root splits into models and operations: "So the root split to me would be between model and ops. model must not contain any ops and must not import from ops either. ops work on the model". [Models and operations](docs/models-and-operations.md) is the design that carries it out, from [research 0018](research-docs/0018-models-and-operations.md#applied) and its grade on [#305](https://github.com/Bitspark/bittype/issues/305#issuecomment-6855741567). It is slice S0 of that grade. **Documents only. No package has moved, and no path of `LAYOUT.md` has changed.**

- **The test.** A responsibility that declares what is true or admissible is model. One that determines whether something is true, interprets it or produces something from it is an operation. A type whose values only a refusing function creates lives with that function on the operations side, so model-side types are plain data. A constraint that exists only as its evaluator is named by the model, and the declared model is an upper bound of what is admitted.
- **Consistency and correctness.** Four levels, stated for the first time: structural consistency, model consistency, language validity and correctness against another model. No guarantee is inferred from another. The envelope, the snapshot, the receipt and the Source are the artifact, the evidence and the admitted artifact that the advice asks for, and four gaps are named.
- **One language's models.** Syntax, analysed semantics, intent and symbols keep separate names, with a stated relation and one test for each form. A shared identity waits for a reader, with a trigger that anyone can check.
- **Intent.** An intended-forms package, which the code calls `model`, becomes a declared table of forms on the model side. One checker and one constructor in the agnostic layer read it, in place of four near copies. The target keeps lowering and coverage. Go's condition that a defined type has a record body is dropped: the choice is the declaration contribution's, its policy makes it already, and no code is written for it anywhere. The page writes out a table type and Go's table for all seven forms, as a sketch for slice S2.
- **The layout.** Two roots. Below `model` the sort first and then the language. Below `ops` the stage matrix as it is. One module. A table places every one of the 129 production packages of `main`: 8 are wholly model, 23 split and 98 are wholly operations.
- **Roles and enforcement.** The role Foundation is divided between the roots, and the role Vocabulary exists under both. The import test carries "a model imports no operation" as one prefix rule with a test that breaks it. "A model contains no operation" is judged in review and gets no check.
- **The order of work.** Slices S0 to S9. The splits of packages that the contribution-contract migration does not change are made on `main`, and the migration's branch merges `main` after each. On that branch the identities of a contribution get their model-side owner first, and then the intended-forms packages are split, before its gate is shown. The scripted move under the two roots comes before the migration merges.
- **Ten further decisions, M10 to M19.** The first version of the page marked nine choices that no rule or accepted page settles, and the research owner [decided them](https://github.com/Bitspark/bittype/issues/305#issuecomment-6856947056) on the same day: the shape of a path below `model`, ten sorts (a language's grammar table lives with its node kinds in its syntax vocabulary), the intent carrier stays whole with the planner, the form table stays a sketch until slice S2, the paths of the operations halves, the role "public part", a declared table in a vocabulary package, nothing refuses Go's record-body condition after the split, and a grammar table names a predicate by an owner-qualified name. [M19](https://github.com/Bitspark/bittype/issues/305#issuecomment-6857366489) adjusts the sorts in one point after the page had checked them against the code: a language's word lists and the names of its predicates are a lexical part below its syntax model, which imports no node kinds.
- **Eight decisions after an independent review, [M20 to M27](https://github.com/Bitspark/bittype/issues/305#issuecomment-6858493249).** A reader that did not write the page read it at `62abbd4`: merge after named changes, and no decision M1 to M19 overturned. The symbol packages of Go and Rust are wholly operations, because their symbol types are sealed. On the migration's branch the publisher name leaves the common mapping package with the profile identities, and by [M28](https://github.com/Bitspark/bittype/issues/305#issuecomment-6859046842) it lives with the identity types of a contribution, where no language is needed to state it. The identities of a contribution move before the intended-forms split. Making that split on the branch is a decision about where a correction is made and no deferral under AC-10, and it is made on `main` if the migration's pull request closes unmerged. The slices wait for what they need: the grammar tables have an agnostic part and a part for each language, and the graph carrier waits for #310. The eleven literal keys of the Go bridge are published with the semantic vocabularies. Two paths, of the typed readers and of symbol admission, are decided again when platform research 0004 is evaluated. The page also answers, slice by slice, what a lane would have had to ask. [M29](https://github.com/Bitspark/bittype/issues/305#issuecomment-6859553686) follows the second round of the review: six methods on the identity types, not three, become functions of the generation contract before the types move; taking the typed readers out of the semantic vocabularies is a part of its slice that waits for a decision, and no deferral; and the work that only the pairs' branch holds has its own row in the order. Five points stay open and are named on the page.
- **A new case.** [bittype/ACX-015](docs/architecture-cases/0015-models-hold-operations.md) records that models hold operations and import operations, with the rules involved and the designed correction. For the four intended-forms packages the correction is made on the branch of the migration of #196, and `main` shows the misplacement until that branch merges, or until the split is made on `main` if its pull request closes unmerged. The case records the reason and both conditions. It is no deferral under AC-10.
- **Clarified, not rewritten.** `LAYOUT.md`, `AGENTS.md`, `CHARTER.md`, [package boundaries](docs/package-boundaries.md) and [generation composition](docs/generation-composition.md) each gain dated clarifications that state the target and say that it is not implemented. Every description of today's code stays as it is.

## The flat-name rule leaves the shared builder and TypeScript — 13 November 2026

Generation no longer refuses two declarations of one name, or a type parameter that is named like a declaration, for TypeScript. The shared builder holds no rule about names across declarations, and the TypeScript Files formatter decides them for each file of a placement. This is the second of the two changes of [#273](https://github.com/Bitspark/bittype/issues/273) and delivers row 8 of [research 0016](research-docs/0016-native-files-placement.md) for the shared builder and TypeScript. With it every done-when item of #273 is met.

- **The shared builder.** `Compile` in `transform/syntax/shared/target/go` identifies a declaration by its planned identity and a parameter by its position, and reads a name only to write it. It no longer refuses two declarations of one name or a parameter named like a declaration: both returned `ErrScope`. It keeps the one rule whose meaning is inside a declaration: two parameters of one declaration cannot share a name. The order of the declarations is the comparator of #272: the name, then the provenance, then the planned identity.
- **Each target states its own rule.** The Go, Rust and C++ targets still select `CheckSingleScope` in their program rule, so their answer to both collisions is unchanged: unsupported. The TypeScript target no longer selects it. Its program rule states only that the type parameters of one declaration have distinct names, which is what it refused before for that case. That rule needs no knowledge of a language, so it has one implementation ([AC-11](https://github.com/Bitspark/platform/blob/main/docs/concepts/architectural-correctness.md#ac-11)): `CheckDistinctParameters` in `transform/syntax/shared/target/go`. `CheckSingleScope` calls it for that half and keeps its own two rules, and the TypeScript target selects it and holds no loop. Whether a language asks for the rule stays its target's choice. A type parameter that is named like its own declaration generates for TypeScript too.
- **TypeScript Files decides names per file.** Two declarations of one name in one file are invalid input, as before, and two files for them are published. A use of a declaration inside a declaration of the same file that has a type parameter of that name would be captured by the parameter. TypeScript Files refuses that placement as unsupported coverage, before a tree is built: a later slice may rename the parameter where that is permitted. The same use with the declaration in another file is published, because the import gets an alias. A use of a global type is captured in the same way, by a type parameter in scope and also by a declaration of its file, and gets the same answer. For generated declarations only a consumer's contribution writes a global type.
- **Four answers changed their category, and each is named.** [The Files document](docs/source.md#failure-categories) says that a later change may not move a refusal from one category to another, and names these four as corrected on this date. Nothing was released with the earlier answers.
  - A captured use that is applied to arguments (`own: U<T>`) and a capture in the constraint of the parameter (`T extends U`), in a placement of existing source: from missing evidence, the compiler's TS2315 and TS2313, to unsupported coverage. A capture is a placement that TypeScript Files judges itself, and the compiler's late answer was in the wrong category.
  - A member that is named like a type parameter of its interface (`interface Box<T> { T: T }`): from invalid input to unsupported coverage. The file is valid TypeScript. The compiler keeps the member and the parameter in one symbol, and this profile does not tell them apart.
  - A use of a global type that a declaration of its file or a type parameter in scope captures: from missing evidence, the compiler's TS2315, to unsupported coverage.
  - A capture whose text still compiles had no category before: the bridge answered `semantic.ErrInvalidRequest`. It is unsupported coverage now.
- **The alias of an import, stated and pinned.** An alias is the local spelling of a use of an import and renames nothing: no declaration and no parameter is respelled. An import keeps the name of its export unless that name is taken in the importing file: by a declaration, by a type parameter, or by a name that another use is written with. Then it gets the first free suffix `_1`, `_2` and so on, and the alias takes its name. The imports of a file are decided in the order of their module specifier and then of their export name. The rule is not new. [The TypeScript document](docs/typescript-type-imports.md#names-in-a-file) states it now, and the tests of `integration/go/typescript_names_test.go` pin the bytes of every file that they publish, among them `import type { T as T_1 } from "./t.js";` for a declaration that a type parameter of the importing record would capture, `import type { Page as Page_1 } from "./alias.js";` for two declarations of one name of which one uses the other, and three imports of one export name as `T_1`, `T_2` and `T_3`.
- **Validity before coverage.** A capture, of a declaration or of a global type, is found in the same pass as the two refusals of relocation and is reported after everything invalid. A placement that also has a path that is no TypeScript path, or that also separates an unexposed declaration from its user, is invalid input. One order is not reached: a member named like a type parameter of its interface is refused while the graph is read, like a script, before the refusals of relocation. A row pins it.
- **Destinations.** An output with two declarations of one name is the case in which a name does not say what is meant. `TestEveryNameUseOfASealedOutputCarriesOneDestination` reads two such TypeScript outputs: every use carries one destination, and the test of the fixture target shows that each reference of the builder is bound to its own declaration.
- **Tests.** Four tests with a fixture target qualify the builder: a target without a program rule builds two declarations of one name and a parameter of that name, with two sites and each reference bound to its own declaration; the Go target still refuses them; the builder still refuses two parameters of one name; and two helpers of one name are ordered by the order of the roots. `TestGenerationNameCollisionsAndPhantomSlots` now runs five sources for all four targets: TypeScript generates the three collisions that are not inside one declaration, and Go, Rust and C++ answer unsupported as before. Thirteen TypeScript tests place the outputs and pin the texts. The table of failure categories gains fifteen rows and has 183.
- **Unchanged output.** A temporary probe recorded what the existing integration tests format and generate, with the inventory, the exposure and the external uses of every generated output. Every record of `main` has the same SHA-256 after the change. The before and after lists of `go test ./...` differ by the new tests, the new rows and the subtests of the collision test, which now has one per target.
- **What a later change may not alter.** That the shared builder holds no rule about names across declarations. That two declarations of one name in one TypeScript file are invalid input and that a captured use is unsupported coverage. The alias rule and the texts that the tests pin. A later change may turn the capture into success by renaming the parameter.

Not done:

- Go, Rust and C++ keep the flat-name rule until their Files stage checks collisions per placed scope: slice 1 of [#161](https://github.com/Bitspark/bittype/issues/161) and of [#159](https://github.com/Bitspark/bittype/issues/159), and [#160](https://github.com/Bitspark/bittype/issues/160).
- Two declarations of one name and one provenance, which two helpers of one name are, are ordered by their planned identity, and that follows the order of the requested roots. The pair is reachable for TypeScript since this change, so the order of the two sites, and the order in which TypeScript Files writes them, is not the same for every order of the roots. It is not reachable for Go, Rust and C++ while they select the flat rule.
- `CheckSingleScope` stays in the shared target package as the rule that three targets select. [Package boundaries](docs/package-boundaries.md) records that as finding 11, which is not decided here.
- The unqualified naming policy does not become TypeScript's default with this change. That is [#274](https://github.com/Bitspark/bittype/issues/274), done-when 10.
- TypeScript Files renames no parameter. The capture check reads every type parameter below the declaration that holds the use, which is exact for the parameters of an alias and of an interface, the only binders of the profile.

## The Rust helper binds a use of a primitive type and states its profile — 13 November 2026

Generated Rust output records the destination `Bool()` at every `bool`, and no evidence could establish it: the Rust helper published bindings for path segments only, so a struct, an alias or a generic parameter named `bool` that captures a use was invisible. This is the remaining part of [#276](https://github.com/Bitspark/bittype/issues/276), decision 2 of its open points: "Rust `bool` gets a Rust-issued symbol and a binding from the helper." With it goes a limit recorded on [#278](https://github.com/Bitspark/bittype/issues/278): the helper did not state its own profile. No generated text and no generated record changes, nothing compares a use with its destination yet, and no Files stage is added.

- **A primitive type has an entity.** The Rust vocabulary publishes one more entity kind, `rust.PrimitiveKind()`, `primitive`. Its entity is named as the language names the type, `bool`, and has no owner, no declaration site and no compiler path, because no crate defines a primitive type. A graph holds one for each primitive type that its source uses.
- **The helper binds every primitive type node,** under the role `target` of a path segment, to what the compiler resolved the name to: the entity of the primitive type, or the struct, enum, alias or generic parameter of that name that captures the use. A node without a binding is unsupported coverage, as a path segment without one is. Every primitive type is bound and not only `bool`, because `u8` is captured the same way; the symbol package still issues `Bool()` only, and a second primitive symbol is an addition there.
- **How `Bool()` is established.** A use reaches it when the binding at its `primitive-type` node names an entity of the kind `primitive` whose name is the symbol's. ## The generated-Files contract takes a typed placement and runs the common admission itself — 13 November 2026

The shared contract for placing generated declarations reads the consumer's placement before the provider runs, and asks the language which evidence one request requires. Before, it handed the placement to the provider unread as the bytes of a setting, and it fixed the required evidence when a formatter was constructed. This is the first of the two changes of [#273](https://github.com/Bitspark/bittype/issues/273) and delivers rows 1, 5, 6, 9, 10, 20 and 27 of [research 0016](research-docs/0016-native-files-placement.md). The Go and Rust Files formatters of [#161](https://github.com/Bitspark/bittype/issues/161) and [#159](https://github.com/Bitspark/bittype/issues/159) are written against it. The second change removes the flat-name rule from the shared builder and from TypeScript. [The Files document](docs/source.md#the-generated-files-contract) describes the contract.

- **A typed placement, issued by its language.** `format.GeneratedFilesInput` carries the sealed output, a `GeneratedPlacement` and the limits. The field `Configuration` is gone, and no placement bytes cross the contract. A placement type belongs to its language. The language issues the value through a `GeneratedPlacementIssuer` and reads it back, as the issuer of an external symbol does. The engine carries the value and does not read it. A placement of another issuer is a refusal with a category and never a failed type assertion.
- **One preparation step per language.** `GeneratedFilesContract` holds the Syntax printer and `Prepare`. It has no `Evidence` and no `Check` field. For one request the step returns the admitted placement, the evidence requirement and the guard. A step that returns without the admitted placement of its request, without a guard or with a requirement that asks for no semantic graph fails the request with `format.ErrInvalidFormatter`, and the provider is not called. `NewGeneratedFilesFormatter` refuses a contract without a step. It no longer refuses a contract without semantic evidence: the requirement belongs to one request.
- **The common admission runs in shared code, before the provider.** The step derives a `GeneratedPlacementView`, each file identity with its path and each declaration handle with its file, and calls `Admit` while it runs. Each refusal is invalid input or an exceeded limit. It accepts a file without a definition and two declarations of one name in one file: it interprets no scope and holds no map of names.

## The compiler bridges enforce their bound on a helper's output — 13 November 2026

The Rust and TypeScript compiler bridges bound what a helper process may write, and the bound did not hold. This is [#296](https://github.com/Bitspark/bittype/issues/296). It is a defect fix in the two private bridge packages. No contract, vocabulary or generated output changes.

- **The defect.** Each bridge collects its helper's output stream and error stream in a bounded writer: 16 MiB for the output stream, and 256 KiB (Rust) or 16 KiB (TypeScript) for the error stream. The type embedded `bytes.Buffer` and so had that type's `ReadFrom`. `os/exec` copies a child's stream into the writer with `io.Copy`, and `io.Copy` calls the writer's `ReadFrom` when it has one. So the bounded `Write` was never called. The lane of #278 showed a helper that wrote 13.8 MB to its error stream and passed the 256 KiB bound of the Rust bridge without an error.
- **The path, as read in the go1.27.0 toolchain.** `os/exec` starts one goroutine per stream that runs `io.Copy(w, pr)`, where `pr` is the read end of a pipe (`os/exec/exec.go:612-616`). `io.Copy` asks the source first (`io/io.go:410-412`). The source is an `*os.File`, and its `WriteTo` hands every writer that is not a Unix or TCP stream connection to a second `io.Copy` over a wrapper that hides `WriteTo` (`os/file.go:265-296`, `os/zero_copy_linux.go:18-23`, `os/zero_copy_stub.go:11-13`). That copy asks the writer and calls its `ReadFrom` (`io/io.go:414-416`), which for an embedded `bytes.Buffer` reads to the end of the stream (`bytes/buffer.go:224-243`).
- **The correction.** The collected bytes are a field, and `Write` is the type's only method. A write that would pass the bound cancels the process. The bridge then returns `semantic.ErrLimit` and no output, as its code already said. A write after the bound was passed is refused too, so the writer never holds a stream with a part missing in the middle. A stream of exactly the bound is read whole.
- **Two copies of the type stay.** The work item asked for one type in a package that both bridges may import under the architecture test as it stands, or the reason for two. A bridge has the role `internal/<language>sem`, and [the layout](LAYOUT.md#dependency-direction) gives it "foundations and its own syntax and vocabulary". The packages that both bridges may import are `contracts/parse/go`, `contracts/semantic/go`, `files/go`, `semantics/go` and `trees/ast/go`. Each is a public carrier or contract. A writer that cancels a child process is neither, and it would become a public name of a shared contract. A new shared private helper would need a new entry in the closed table `foundationRules` and a wider role for the bridges, and this change adds no allowance. The type has four fields and one method, and each bridge now has a test with a real process.
- **Tests.** `TestHelperOutputBound` in each bridge package starts a real child process, the test binary itself, through the bridge's exported `Check`. Both bridges already take the executable as an argument, so no test seam was added. The child writes exactly the bound, or one byte more, to its output stream or to its error stream. At the bound the bridge reads the stream whole. One byte over is `semantic.ErrLimit` and an empty output, for a child that exits and for a child that never exits by itself. The second kind shows the cancellation: the bridge returns well inside its own deadline of 30 seconds, and the child's connection to the test ends, which only the end of the process does. No goroutine of `os/exec` outlives a call. `TestBoundedBufferOnlyWrites` requires that the type has no method but `Write` and that a write after the bound is refused. On `main` the tests fail: the bridge returns no error and the whole oversized stream, and it does not cancel the child. 16 mutants per bridge, each of which removes or shifts one part of the check, each fail a test: the bound removed, off by one in both directions and for each stream, the cancellation removed, a `ReadFrom` added again, the error dropped, and one stream left unchecked.
- **Nothing relied on the missing bound.** A temporary probe recorded what the TypeScript helper writes in the 96 runs of the test suite. The largest output stream is 48,771 bytes and the largest error stream 1,160 bytes. The Rust helper does not run on the workstation, and the hosted checks run its tests with the bound in force.
- **Unchanged output.** No generation or formatting package imports a bridge's writer, and none is touched. The lists of `go test ./...` before and after differ only in the 16 new tests and subtests.

- The other limits of the bridges, among them the deadline of 30 seconds, and anything in a helper.
- `tools/provider-matrix/report/go/load.go` has a third writer of the same shape, `boundedOutput`, which embeds `bytes.Buffer` and collects the output of the `go` command against a budget. By reading, `os/exec` fills it the same way. It was not run and is not changed here.

## The Rust bridge publishes declared and effective visibility, makes an unusable public record observable, and takes an explicit environment — 13 November 2026

The Rust semantic profile gains the facts that a Rust Files stage needs to check the visibility it decides, and an environment that a consumer states. This is [#278](https://github.com/Bitspark/bittype/issues/278) and delivers rows 23 and 24 and the Rust part of row 28 of [research 0016](research-docs/0016-native-files-placement.md). No Rust formatter exists yet, and generation is unchanged. The profile's vocabulary and its configuration change, so the profile has a new version and the helper profile is `captured-types-2`.

- **Two visibility facts, kept apart.** Every captured module below the crate root, alias, struct, enum and trait has a `declared-visibility` and an `effective-visibility` fact. The declared fact is the compiler's resolved form: public, or restricted to a module entity, and the crate root is one. `Declaration.Visibility()` reads it. The effective fact states an audience, a path and whether the audience can name the declaration through it. In this profile the audience is another crate and the path is the definition's, so it holds exactly when the declaration and every module around it are declared public. `Declaration.Effective()` reads it. `mod m { pub struct D {} }` gives `D` a public declared fact and an effective fact that says no.
- **The effective fact comes from the compiler.** The helper reads the compiler's effective visibility at the level that means direct access. It is not the compiler's "reachable", which includes types that another crate meets and cannot name: a test has such a type and the fact says that it is not nameable.
- **A field has the declared fact in the same form.** `Field.Public` is replaced by `Field.Declaration`, whose `Visibility()` tells `pub(crate)` from private. The helper no longer writes the yes or no into the fields term. This is incompatible for a caller of `Field.Public`. None is known in bittype, and nothing is released.
- **A missing fact never means private.** Both readers fail with `rust.ErrMissingFact` when the fact is absent, present twice or in another form. The forms are exact. A declared term carries no data. The data of an effective term is one object with the members `Audience`, `Path` and `Nameable`, each once and spelled so, and nothing after it. The `fields` term, whose decoder is older than this change, is read as strictly: each field by exactly `Name` and `Entity`. `Type.Fields()` returns three results now, the fields, whether the type has the fact, and an error: a type without the fact has no fields, which is no error, and a fact that is present twice or in another form, or a field whose entity the graph does not have, is `rust.ErrMissingFact` and never reads as "no fields". This is incompatible for a caller. Its 14 callers are all in tests. A repeated member, a member in another case, an unknown member and data after the value fail. That also pins the member names between the helper and the Go side: a helper that writes `audience` passed every test before the review.
- **A public record whose field has a more private type is observable.** `pub struct Public { pub field: Hidden } struct Hidden {}` is legal Rust and stays analyzed. The helper forces the compiler's lint `private_interfaces` with `--force-warn`, receives its own diagnostics and publishes each as a `private-interface` fact on the declaration the compiler reports it at, with a reference to the more private declaration. `Declaration.PrivateInterface()` reads it. The same source with `pub struct Hidden` has no such fact. The probe that the research still owed is answered: `-W` after `-A warnings` reports nothing, `--force-warn` reports the lint as a warning, and `-D` would make it a compiler error and a rejected validity. For the default of a type parameter, `pub struct P<T = Hidden>`, the compiler reports the item itself. The helper withholds every warning from its error stream, and a test of the bridge package runs the helper and reads that stream. A record with 600 such fields resolves with 600 observations.

## The Files stage tells unsupported coverage from invalid input — 13 November 2026

A Files formatter answers each refusal that it decides in one of four categories: invalid input, unsupported coverage, missing evidence or an exceeded limit. A caller tells them apart with `errors.Is`. Before, a formatter could not say "this input is well formed, and this profile does not cover it yet": every refusal was invalid, one had no category and one was a raw decoder error. This is [#271](https://github.com/Bitspark/bittype/issues/271), row 35 of [research 0016](research-docs/0016-native-files-placement.md) and the first of its eight work items. It changes failure values, and it refuses one input that was admitted: a placement that names a member twice. No other admitted input changes and no output changes.

- **The value and the rule.** `source/go` declares `ErrUnsupported` beside `ErrInvalid`, `ErrStale` and `ErrLimit`, and each of the four has its own comment. A refusal is unsupported coverage when a later slice can admit the same input, and it is invalid input when no later slice can. The same input is judged under the same vocabulary: an input that is malformed under the published vocabulary of a setting or a placement type is invalid, and an input that is well formed under it and outside what the implementation covers is unsupported. Missing evidence stays `semantic.ErrEvidenceUnavailable`, and a limit stays `source.ErrLimit`.
- **Unsupported coverage in TypeScript.** An import form other than a named type import, which had no category. A file that is a script, a file without a declaration, a capture without files, and a path that TypeScript reads and the profile excludes (`.d.ts`, `.mts`, `.cts`, `.tsx`, or `#`, `%` or `?` in a TypeScript path), which were invalid input. [The TypeScript document](docs/typescript-type-imports.md) states these as limits of its profile, and row 30a of research 0016 defers the form that admits a file without a declaration.
- **One function joins a category, and nothing is replaced.** `source.WithCategory` says which category a value of another layer carries: `files.ErrLimit` and `semantic.ErrLimit` are an exceeded limit, `files.ErrInvalid` is invalid input, and every other error is returned as it is. The result matches the category and still matches the value. The publisher calls it for its inventory check, and each formatter for its own inventory check and for the capture of its fresh output. ## A sealed output lists every declaration it owns and issues the handles a placement is built from — 13 November 2026

`generation.Output` has a complete inventory of its declarations, and each record carries a handle that belongs to that one output. This is [#272](https://github.com/Bitspark/bittype/issues/272) and delivers rows 10 and 12, the inventory part of row 19 and the order basis of row 5 of [research 0016](research-docs/0016-native-files-placement.md#applied). The generated output of every existing test is unchanged: a temporary probe recorded 144 records in a full run before and after, 88 formatted texts, 38 output trees, 8 placed TypeScript trees and 10 Files records, and each has the same SHA-256. The placement types, the shared admission and the removal of the flat-name rule are #273.

- **The inventory.** `Output.Inventory()` returns one record for each declaration of the snapshot and no other record, in the order of the sites. A record carries a handle, the site, the role, the provenance and the values that the owner of the description issued. The roles are requested, dependency and helper. They are not a closed set: a further role may be added, and a reader refuses a role it does not know. The provenance is the list of the declaring sites of the source declarations that the declaration represents, and it is empty for a helper. There is no grouping field.
- **Where the facts come from.** The planner knew the source declaration of each planned declaration and which of them are helpers, and `PlannedDeclaration` had no field for either. It now has `Role` and `Provenance`. `Role` replaces `Exposed`, which stated one of the three roles. The shared constructor held the node of every declaration in a local map and returned only the requested ones. It now returns the site of every planned declaration in `Assembly.Declarations`, once for all four targets. `Assembly.Exposed` is removed: the kernel derives the exposed sites from the plan and the listed sites, so the requested records are exactly the sites of `Exposed()` by construction. The planner hands a target a copy of each declaration it asks the target to check or to build, so a target that overwrites what it was handed changes no record.
- **The handle.** A `DeclarationHandle` carries its output, as an `ExternalSymbol` carries its issuer. `Output.Resolve` returns the record of a handle that this output issued and fails with `ErrScope` for any other. A second run of the same plan has the same tree identity and the same node numbers, and it refuses the handles of the first run.
- **Issued values.** A naming intent and the access a helper requires are not meanings of the kernel. Their owner creates a `ValueIssuer`, a declaration recipe or a helper recipe states the issued value in `Values`, and the kernel carries it to the record. Only the issuer reads the content through this API. The planner refuses a value that no issuer issued with `ErrInvalid` and charges each value to the output budget, the bytes of its content and one byte for the value. Limit: the content is hidden by the API only, as an external symbol's key is. Reflection reads it, a value compares equal wherever it is carried, and whoever holds a value can state it again in another description. Formatting a value, or a record or a description that holds one in an exported field, prints whether it was issued and never its content; formatting an `Output`, a `Program` or another struct that holds a value under an unexported field prints the content. No builtin mapping states a value yet. The naming intent is #274.
- **What sealing checks.** `seal` fails with `ErrIncomplete` when the assembly lists another number of declarations than the plan has, and with `ErrScope` when a site lies outside the snapshot, is listed twice or lies inside another listed site. The last check needs no knowledge of a language: it refuses the root node beside any other declaration, and a node inside another listed declaration. The shared constructor guarantees that a site is the node the target's lowering returned for that declaration, emitted once. Where that node sits is the lowering's decision: C++ declarations are the children of a namespace. The constructor returns no assembly when a planned declaration has no node in the unit.
- **The comparator.** The shared constructor seeds its walk in the order of `compareDeclarations`. The walk emits each declaration after the declarations it uses, so the comparator fixes the node numbers and the sites. Its key is the name, then the provenance, then the planned identity. The provenance is the planner's own fact. The origin on a description is the mapping's optional statement, so it is not part of the key. Before, the comparator returned 1 for two equal names in both directions. That could not be reached, because the constructor refuses equal names first, and it still does. Limit: two declarations of one name and one provenance, or two helpers of one name, are ordered by the planned identity, which follows the order of the requested roots.
- **The shared contract changed**, and platform's rule AC-08 asks why. The capability is to address every owned declaration without reading native syntax, and to bind a placement to the output it was written for. The generation kernel is the layer, because it issues declaration identity: only the planner knows the roles and the source declarations, and only the kernel seals the capture that a site belongs to. Every language's Files stage uses the same records and handles, and a mapping or a target language adds a meaning by issuing a value without a change to the kernel. The boundary change is not only an addition: a target that fills its own `Assembly` now lists every declaration. The four targets build through the shared constructor and are not edited.
- **Tests.** Twenty tests are new, with 36 subtests. The independent fixture generates three roots that need one dependency and one helper, and the test selects the five declarations by role, provenance and issued value and reads no `name` attribute of the output. One plan is run twice and each run refuses the handles of the other. A fixture target that omits, adds or repeats a site, or lists one outside the snapshot or inside another listed site, is not sealed. A target that overwrites every value and every parameter name of the declarations it is asked to check changes neither the records nor the generated unit, for a source declaration and for a helper. The pagination module gives a complete inventory in TypeScript, Go, Rust and C++, and four independent records requested in descending order of their names get ascending sites in all four. An assembly of two trees gives its records in the order of the trees. The comparator is checked for every pair of ten declarations, whose origins and planned identities run against the order wherever an earlier part of the key decides. 55 seeded faults each fail a test: four restore the behaviour before this change, 48 remove or change one check, one copy or one part of the key, and three are the faults that an independent review found surviving the first version of these tests. The two existing tests of `seal` build the assembly and the plan in the new form and assert what they asserted. The independent fixture's library states a naming intent for each declaration it describes and an access for its helper, which changes no generated text.
- **Documents.** [Planning and running type generation](docs/generation-planner.md#the-declaration-inventory-and-its-handles) describes the inventory, the handle, the issued values and the order of sites, and records the justification and what a later change does not alter. ## The naming design: generation records an intent, each language realizes the spelling — 13 November 2026

[Naming](docs/naming.md) is the accepted design for who decides a native name and its visibility. It comes from rows 11, 13 and 14 of [research 0016](research-docs/0016-native-files-placement.md) and from the comments of its owner on [#274](https://github.com/Bitspark/bittype/issues/274): the six decisions of 12 November 2026, the [seven of 13 November 2026](https://github.com/Bitspark/bittype/issues/274#issuecomment-6838436844) on the points that the first version of the page left open, the [eight after an independent reading](https://github.com/Bitspark/bittype/issues/274#issuecomment-6839006959) of the page, and [one correction](https://github.com/Bitspark/bittype/issues/274#issuecomment-6839289646) after its second reading. It answers [#268](https://github.com/Bitspark/bittype/issues/268). This entry adds and changes documents only. No target has changed a name, and the page says so at its head.

- **Three things that were one string.** A declaration's identity, which alone is authoritative for references. The naming intent, which generation records: the mapping's chosen name, the module's identity as its full pin, the identity of the naming policy, and the spelling that the policy produced. The realized spelling, which a language's Files stage publishes.
- **Owners.** The mapping chooses the name, in a capitalised form that is the same for all targets, and spells it under the policy. The consumer's composition selects the policy, a named value that it gives to the declarations mapping of each pair. The unplaced tree's name is the spelled intent. Each language checks that spelling under its own rules: its reserved words, in Go the case of a name, and in its Files stage the collisions of a placed scope.
- **Refuse, not rename.** In the first slices a target refuses a spelling it cannot publish. An escape rule is a later, explicit rule. Rust refuses `Self` as unsupported coverage, and the other targets keep `Self`. The refusal of a name that contains `__` moves from the shared naming function to the C++ target.
- **Exposure.** `Exposed()` stays the list of requested roots. The page states what an exposed declaration must be in TypeScript, Go and Rust, and the rule that required access is established and realized access stays within authorized access. The request states the access of its roots, and a contribution states the access of every declaration it introduces. So the Go optional helper is realized exported. Files never widens access on its own.
- **Which outputs a language admits.** Go and Rust admit only outputs in which every source declaration in the public representation of an exposed one is itself a requested root. A refusal names every offending declaration. In the structural profile that covers every dependency. TypeScript admits an unexposed declaration in the body of an exposed one within one module, as `TestGeneratedFilesPreservePublicationIntent` pins. Its refusal of a placement that separates the two stays invalid input, as #271 decided. The rule for both: a refusal is unsupported coverage when a later slice can admit the same input, and invalid input when no later slice can.
- **Go.** Go's rule is its own, and it is a check: a spelling is exported when it begins with an upper-case letter, and Go Files refuses a declaration that requires public access and whose spelled intent is not exported. It renames nothing. Go's unexported spelling was defined by the decisions of 12 November 2026 and is deferred by those of 13 November 2026, because nothing in the first slices realizes it. The page specifies no unexported form.
- **The module-pin prefix** is today's default and becomes one of two policies. It becomes selectable first, with unchanged output. Unqualified names become a target's default once that target's Files stage owns collisions: TypeScript with #273, Go and Rust with slice 1 of #161 and #159.
- **What is fixed, and when.** The record of intent and the rules of TypeScript, Go and Rust, before the plan envelope is declared stable and before the first release. Each change of a default lands before that too. C++ is excepted. That a plan entry records no realized native name is what the design asks of #195, and is not fixed by it.
- **Research 0016.** In the table "Applied", row 13 has the validation that the decisions of 13 November 2026 give, the new row 13a defers Go's unexported spelling with its trigger, and rows 13, 14, 14a, 23 and 29 carry dated annotations. The submitted document and the advice are unchanged.
