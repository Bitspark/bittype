# Response to research 0009

**I would keep source witnesses as a useful option, but replace the goal of universal native enforcement with several precisely defined admission profiles.** The common contract should preserve an established source judgment and the selected representation association. Each target must then state which native expressions it admits, where it checks them, and which consumer operations its guarantee covers.

Two findings materially change the proposed direction:

- **TypeScript evidence bounds can admit an invalid application through `never`, even when the resulting payload type is inhabited.** Invariance does not repair this.
- **The Go private-evidence sketch has an inference hole.** An exported singleton constraint can let a consumer infer an unpublished instantiation of the private evidence constructor. Selectively exporting aliases therefore does not establish an issuance boundary.

Rust and C++ offer useful alternatives, but neither makes ownership, configuration, or rejection timing disappear.

I take the Horos semantics and inspected baseline in the brief as premises. The language conclusions below use primary references; the examples are specification-based reasoning, not reported compiler results. I have not run compilers or implemented anything.

## 1. Define preservation around source-facing applications

### Keep three propositions separate

For a fixed checked source world \(H\), assumption environment \(\Gamma\), and representation configuration \(c\), distinguish:

| Proposition | Meaning | Authority |
|---|---|---|
| \(\Gamma \vdash_H S : K\) | The canonical expression satisfies the kind under the stated assumptions. | Horos |
| \(R_c(S)=N\) | Configuration \(c\) selects native type \(N\) for that canonical expression. | The selected mapping and generation contract |
| \(v \models S\) | A particular value denotes a valid value of the canonical description. | Outside this consultation |

The second proposition is an association, not a value-conformance theorem. Even a perfectly controlled certificate for the first two propositions does not establish the third.

Also, \(S\) must retain enough identity for mapping selection. Two aliases may normalize to the same observations for membership while selecting different type-owned mappings. A witness that preserves only the normalized structural description can therefore lose information that generation still needs.

### The soundness promise

I recommend this contract:

> Within the profile’s declared native argument language and consumer-operation domain, every application admitted at the specified checking point has a declared canonical interpretation. Its source application is valid under the corresponding assumptions, and its native representation agrees with the selected configuration.

“Has a declared canonical interpretation” matters. The weaker statement “there exists *some* valid source type that could explain this native payload” permits representation collisions to conceal the source argument actually intended.

For open applications, the contract is conditional. A certificate for

\[
X:\mathrm{Tree}\ \vdash\ \operatorname{list}(X):\mathrm{Tree}
\]

cannot become an unconditional certificate for arbitrary lists. Native assumptions must correspond to the original source assumptions, and a concrete application must discharge them.

For a profile that intentionally admits **sets of source choices**, such as a TypeScript selector over a union of generated keys, define that interpretation separately. A union of choices need not denote one canonical expression.

### Completeness should be required over an announced domain

Soundness alone allows an implementation that rejects everything. Require relative completeness:

> Every established source application in the profile’s explicitly specified representation and composition domain has an expressible native application with the promised behavior.

That domain must be described independently of “whatever the implementation happens to accept.” It can be finite, or generated by a specified set of compositional rules, and it can include explicit resource limits.

Completeness here is relative to **established judgments**, not every mathematically true judgment. `Unproved` and `Exhausted` remain failures to establish admission. Neither becomes a permissive encoding.

Likewise, a missing native certificate means “unavailable in this API/domain”; it must not be exported as a source theorem that membership is false.

### The exact condition for direct payload bounds

Suppose admission depends only on \(N=R_c(S)\). To be both sound and complete for kind \(K\), membership must be constant over every representation collision:

\[
R_c(S_1)\equiv_N R_c(S_2)
\quad\Longrightarrow\quad
(S_1:K \iff S_2:K).
\]

This is necessary, though not sufficient: the target must also be able to express the required predicate, with its actual subtyping and comparison rules.

Full injectivity of the representation is stronger than necessary. What matters is that each representation-equivalence class is homogeneous for the particular membership question.

If a class contains both an admitted and a rejected source description, a payload-only bound has two choices: reject the entire class and lose completeness, or accept it and lose soundness. Witnesses are useful precisely because they can retain the distinction that the payload discarded.

### Admission and retained identity are independent promises

A checked alias may validate an application and then erase its source and evidence arguments. That can be a useful API.

It does not follow that:

- an arbitrary value of the resulting payload type carries evidence;
- later generic inference can reconstruct the canonical argument;
- assignment to the alias proves that the value came through the checked application.

If those later operations matter, retain a descriptor alongside the payload or select a wrapper profile. Do not silently change alias interchangeability to obtain that stronger property.

## 2. Recommended profiles and trust boundaries

I would document the following combinations explicitly:

| Profile | Argument domain | Checking point | Extension model | API promise |
|---|---|---|---|---|
| **Representation** | Source applications supplied to generation; ordinary native payload generics afterward | Source analysis | Separately generated compatible modules | Constraint erasure is permitted |
| **Named applications** | Explicitly requested, generated applications | Source analysis and generated declaration checking | Further source generation adds applications | Ordinary native aliases where supported |
| **Bounded native admission** | Generated descriptors and an explicitly supported certificate domain | Target-specific instantiation or normalization | Closed owner or generated composition owner | Admission may be followed by erasure |
| **Retained association** | Controlled generated descriptors | Specified native well-formedness checks | Sealed or explicitly trusted extension | Source/configuration identity remains represented |
| **Trusted extension** | Additional generator-produced descriptors and facts | Native checks plus trust in issuers | Independently generated modules under a stated contract | Consumers cannot treat arbitrary handwritten grants as established facts |

The last row is not automatically stronger than the others. It exchanges language-enforced closure for trust in additional issuers.

The trusted components include Horos’s established judgments, the source adapter, the mapping provider, certificate generation, and the selected target compiler configuration. An analysis receipt binds facts to input; it does not independently make a faulty evidence emitter sound.

**Soundness, relative completeness, separate compilation, and early rejection can coexist within a suitably restricted domain.** They cannot all be promised for unrestricted native expressions, arbitrary overrides of imported headers, and every target’s earliest textual type occurrence.

A further boundary is important: if “permitted consumers” means only code produced by your own generator, source analysis already supplies most of the admission guarantee. Extra native proof arguments may help composition and diagnostics, but should not be advertised as protection against ordinary independently authored native code.

## 3. Target-language assessment

### TypeScript: upper-bound evidence is insufficient

The strongest counterexample is broader than `TreePage<never>`.

For a candidate of this form:

```typescript
type CheckedPage<S, N, P extends Evidence<S, N>> = Page<N>;

type Wrong = CheckedPage<WireTextType, number, never>;
const value: Wrong = { items: [123] };
```

`never` satisfies the evidence bound. The result is an inhabited `Page<number>`, even though no certificate for the intended source tuple was supplied. This follows from TypeScript’s documented bottom-type behavior. It survives making `Evidence` genuinely invariant. [TypeScript 2.0](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-2-0.html?utm_source=chatgpt.com)

For the single-parameter sketch, `TreePage<never>` still forms. Returning outer `never` can provide a normalization-level filter; it does not create a formation diagnostic. Returning `Page<never>` is weaker because an empty items array remains possible.

There is also a structural fabrication problem with the brief’s property-based evidence:

```typescript
type Fake = { [K in keyof PersonInTree]: never };
```

For that evidence shape, every required property exists with a bottom type. The consumer need not spell the private symbol. This illustrates why excluding only the primitive type `never` is insufficient: a structural object can contain impossible properties without itself being represented as primitive bottom. This is a deduction from mapped types and structural compatibility. [Mapped Types](https://www.typescriptlang.org/docs/handbook/2/mapped-types.html?utm_source=chatgpt.com)

**Invariance remains useful for ordinary widening mistakes.** A function-valued property using each relevant parameter in both parameter and result positions is a plausible mechanism under `strictFunctionTypes`; method syntax has different variance behavior. A `readonly native: N` property is not invariant. Nor can an `in out` annotation force structural invariance where the structure does not provide it. [typescriptlang.org](https://www.typescriptlang.org/tsconfig/strictFunctionTypes.html?utm_source=chatgpt.com)

A private instance member offers stronger nominal provenance than an ordinary structural brand. A private constructor alone restricts construction, rather than naming all instances of a public generic class. Neither repairs the bottom-type admission issue. [Type Compatibility](https://www.typescriptlang.org/docs/handbook/type-compatibility.html?utm_source=chatgpt.com)

**Unions require an explicit interpretation.** If a union of witness keys means “one of these source applications,” distribution must preserve the whole application:

```text
Page<string> | Page<boolean>
```

Projecting the representation first can instead produce:

```text
Page<string | boolean>
```

which allows mixed collections. TypeScript’s conditional distribution rules make these different constructions. Disabling distribution indiscriminately does not solve the correlation problem. [Conditional Types](https://www.typescriptlang.org/docs/handbook/2/conditional-types.html?utm_source=chatgpt.com)

My initial TypeScript recommendation is:

1. Offer source-checked named applications.
2. Optionally offer a **finite generated selector** whose atomic keys select complete applications.
3. Define unions as choices between complete applications and bottom as the empty selection.
4. Derive payloads from a closed configuration-specific table; do not ask consumers to supply an independent `N` plus structural evidence that it matches.

A type-alias table is preferable to an augmentable interface as the authority. Generated unique-symbol identities can distinguish keys, but packages must reuse the actual exported identity rather than redeclare a same-named symbol. [Everyday Types](https://www.typescriptlang.org/docs/handbook/2/everyday-types.html?utm_source=chatgpt.com)

This is a bounded normalization contract, not unrestricted formation enforcement. Pin strict compiler settings, exclude `any` and declaration-forging operations from the guarantee, and do not interpret arbitrary witness intersections as canonical source intersections.

If an open enforcing `TreePage` is requested under a stricter formation profile, report it as unsupported. A list of concrete exports is not an implicit replacement.

### Go: exact identity helps, but the private issuer is inferable

Go has useful ingredients. Defined generic types preserve their argument identities even when their underlying representation is empty. Thus the brief correctly rejects aliases of `struct{}` as distinct source tokens. [The Go Programming Language](https://go.dev/ref/spec?utm_source=chatgpt.com)

Generic aliases are fully supported from Go 1.24. Their parameter constraints can differ from those of the aliased type, while successful instantiation still yields the same aliased type. That supports admission followed by erasure. [The Go Programming Language](https://go.dev/doc/go1.24?utm_source=chatgpt.com)

**However, the proposed private constructor does not establish selective issuance.**

Assume package `a` exports the brief’s `TreeEvidence` and `TreePage`. Consider this consumer:

```go
func forge[S, N any, P a.TreeEvidence[S, N]]() a.TreePage[S, N, P] {
    var result a.TreePage[S, N, P]
    return result
}

var forged func() a.Page[string] = forge[WireType, string]
```

No function execution is needed.

The explicit arguments determine `S` and `N`. Go supports inference in the function-assignment context, and an unknown type parameter with a single exact, non-tilde constraint term can be inferred to that term. Here the missing `P` becomes the private instantiation:

```text
a.evidence[WireType, string, a.treeKind]
```

The type exists because the private constructor accepts arbitrary arguments. Its unpublished spelling does not prevent inference from selecting it. The inference rule and its implementation directly support this deduction. [The Go Programming Language](https://go.dev/ref/spec?utm_source=chatgpt.com)

The alias’s constraint check still happens. The problem is that the native relation accepts a type whose existence was mistakenly treated as proof of issuance.

A defensible repair must make invalid tuples **actually absent from the admissible relation**. For a finite domain, the logical condition is:

\[
\{\operatorname{evidence}(S,N,K)\}
\cap
\{\text{actually issued certificate types}\}.
\]

An inferred private instantiation for an unauthorized tuple then fails the issued-type restriction. This repairs the logical flaw; the expressibility and completeness of a particular parameter-dependent Go intersection still need later validation. I would not describe that generic spelling as established by this consultation.

A private-method interface is not a substitute. In a type-only setting, a basic interface can satisfy itself, and a consumer can embed an exported interface to acquire its private method set without possessing an issued proof object. Go’s own API-compatibility documentation explicitly discusses the embedding route. [The Go Programming Language](https://go.dev/ref/spec?utm_source=chatgpt.com)

For direct payload constraints, exact types and underlying-type sets are different domains: `string` and `~string` cannot be interchanged casually. Neither supplies a general recursive predicate over every field of an unknown native record. [The Go Programming Language](https://go.dev/blog/intro-generics?utm_source=chatgpt.com)

My Go recommendation is therefore:

- **Established floor:** generated named applications.
- **First stronger candidate:** a finite relation of issued source/representation tuples, with real identity distinctions and constrained aliases.
- **Deferred:** open certificate families until their admission relation is justified independently of private-name hiding.

An open generic may remain open over a finite admitted argument domain. If the target cannot express that publication, reject it explicitly rather than replacing it with concrete applications.

### Rust: separate alias bounds, projection gates, and wrappers

The brief is right about ordinary aliases: bounds on their generic parameters and `where` clauses are not generally checked at use sites under the ordinary semantics documented by the current lint. The feature-gated alternative mentioned there should not silently enter a stable baseline. [The rustc book](https://doc.rust-lang.org/rustc/lints/listing/warn-by-default.html?utm_source=chatgpt.com)

But a demanded associated-type projection is materially different. Conceptually:

```text
TreePage<C, S> = <Gate<C, S> as CheckedTreePage>::Output
```

The applicable implementation must require the membership obligation and the selected association. Resolving its `Output` then requires selecting that implementation.

This also gives `Ignore` a possible alias-preserving route: the associated output may be a constant text type, while implementation selection still requires the input’s membership. A dead bound on an ordinary alias does not do that. Associated types are defined through implementations, which is the relevant mechanism here. [The Rust Reference](https://doc.rust-lang.org/reference/items/associated-items.html?utm_source=chatgpt.com)

**Promise rejection at specified well-formedness or demanded-normalization points.** Do not promise rejection at every textual mention. Rust’s compiler guide explicitly documents incomplete checking of free alias right-hand sides, including an example involving `Vec<str>`. Even placing a constrained wrapper inside an unused alias does not establish universal earliest rejection. [Rust Compiler Development Guide](https://rustc-dev-guide.rust-lang.org/analysis/well-formed.html?utm_source=chatgpt.com)

A nominal wrapper remains useful when persistent association is desired. It changes type identity and access syntax, so it belongs in a separate profile.

For controlled membership:

- Use actual generated trait implementations, with a private-supertrait seal where downstream extension is prohibited.
- Preserve `Sized` on type-only witnesses/evidence. Broadening to `?Sized` can admit nameable trait objects that implement their base trait without requiring a constructible concrete certificate.
- Keep representation separate from membership: one configuration association should serve both `Tree` and `Data`.

The sealing pattern and trait-object behavior are documented Rust mechanisms. [Rust API Guidelines](https://rust-lang.github.io/api-guidelines/future-proofing.html?utm_source=chatgpt.com)

For association ownership, a local configuration as the implementing type—conceptually `Config: Representation<S>`—is useful. It avoids globally fixing `PersonType::Repr` and can avoid orphan-rule ordering problems. A local certificate type can similarly solve ownership, but its locality alone does not establish the source theorem. [The Rust Reference](https://doc.rust-lang.org/reference/items/implementations.html?utm_source=chatgpt.com)

Do not translate a kind union into potentially overlapping blanket implementations such as “every Text member is Tree” and “every Bool member is Tree.” Source disjointness is not automatically available to Rust coherence. Emit deduplicated concrete facts or structurally disjoint witness-family implementations. [The Rust Reference](https://doc.rust-lang.org/reference/items/implementations.html?utm_source=chatgpt.com)

The useful initial Rust domain is controlled, sized descriptors with generated membership facts, followed by a carefully specified choice between wrapper checks and projection normalization.

### C++20: constrained aliases are useful; customization is the boundary

C++20 directly supports constraints on alias templates. Forming a specialization name requires satisfying the associated constraints, with dependent cases checked through substitution. Thus `Ignore<S>` can retain an admission constraint even when its alias result is a fixed text type. Within a dependent `requires` expression, rejection can mean an unsatisfied requirement rather than an error for the entire translation unit. [timsong-cpp.github.io](https://timsong-cpp.github.io/cppwp/n4861/temp.constr?utm_source=chatgpt.com)

After successful substitution, the alias denotes its resulting type. It does not retain a separate source identity. [timsong-cpp.github.io](https://timsong-cpp.github.io/cppwp/n4861/temp.alias?utm_source=chatgpt.com)

The main challenge is controlling positive facts. Concepts cannot be specialized, but supporting class or variable templates can. A consumer-written positive specialization of a membership table is an ordinary customization operation unless the profile excludes it. Private placement alone is insufficient because explicit-specialization declarations have special access-checking rules. [timsong-cpp.github.io](https://timsong-cpp.github.io/cppwp/n4861/temp.concept?utm_source=chatgpt.com)

A useful finite alternative is a concept admitting exact identities from complete, nongeneric generated descriptor classes, with fixed source/configuration/representation metadata. A lookalike or derived type is not the same descriptor. This avoids making an extensible positive-membership table the authority.

That proposal still assumes consumers respect the definitions and the contracts of the type-identity machinery. It is finite, and it does not establish an unbounded open descriptor language. Generic descriptor families require a separately justified mechanism or an explicit prohibition on unauthorized supporting specializations.

Separate generation must also settle declaration visibility before relevant uses. C++20 does not permit identical atomic constraints to change satisfaction at different program points; such a program can be ill-formed without a required diagnostic. Certificate extension cannot behave as late registration. [timsong-cpp.github.io](https://timsong-cpp.github.io/cppwp/n4861/temp.constr.atomic?utm_source=chatgpt.com)

## 4. Recursive kinds and recursive representations are separate questions

I would distinguish three cases.

**First, recursive kinds classifying nonrecursive represented types.** `Tree` and `Data` can be recursive source definitions while `Person` is an ordinary finite record. Horos can establish membership, and the native output can carry one finite fact. The target needs no recursive kind evaluator.

**Second, an already-proved recursive source description.** Once a native representation is supported, its membership can likewise be exported as one concrete certificate. A finite observation graph with a coinductive source proof does not require a coinductive native trait derivation.

**Third, previously unknown recursive families constructed by native consumers.** This requires a new native admission argument. Neither a finite certificate list nor successful native recursive type checking establishes equivalence with Horos’s greatest-fixed-point semantics.

A finite set of checked compositional rules can admit arbitrarily many **finite constructions**. That is already useful and differs from both a finite catalogue and arbitrary recursive membership. For example, a checked rule that Tree membership is preserved by `list` can support finite list nesting.

The rule must actually be established for the kind concerned. “Membership in any \(K\) implies list membership in \(K\)” is false.

According to the supplied baseline, recursive native declarations remain unsupported. Keep that representation limitation explicit even if membership is already proven. Compiler expansion limits are also independent of source truth; TypeScript’s documented recursion heuristics illustrate why successful source analysis cannot promise unlimited target normalization. [TypeScript 4.5](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-4-5.html?utm_source=chatgpt.com)

## 5. Composition should reuse facts and associations separately

### Ownership and reuse

I would separate the following artifacts:

| Artifact | Configuration-relative? | Reuse condition |
|---|---|---|
| Canonical declaration/application identity | Normally no | Same resolved source identities and effective environment |
| Membership theorem, including assumptions | No, if the source world is unchanged | Same subject, kind, assumptions, and checked dependencies |
| Native source witness | Depends on its design | Reuse the actual exported native identity, or supply an explicit bridge |
| Representation association \(R_c(S)=N\) | Yes | Same selected association and relevant dependencies |
| Evidence combining membership and representation | Yes | Both the theorem and association remain applicable |
| Complete native generic declaration | Relative to its declared dependencies | Its header, representation equations, and admission contract remain compatible |

A source witness can be configuration-independent if it contains no fixed representation projection. A globally fixed `PersonType::Repr` cannot serve that role while allowing consumer overrides.

Two configurations may legitimately have different associations for the same source identity. Within one configuration, membership in different kinds must consult the **same** association.

### The Person override

Suppose B selects `Person -> external.User`.

The source theorem `Person : Tree` survives if the canonical source and kind dependencies are unchanged. An evidence artifact for the tuple

```text
(Person, A.Person, Tree)
```

does not thereby authorize

```text
(Person, external.User, Tree).
```

B needs its own selected association and whatever configuration-specific evidence its profile requires.

However, this does **not** imply that every imported generic becomes unusable. If A’s exported `Page<T>` is genuinely parametric in its payload argument, B may be able to use:

```text
A.Page<external.User>
```

through that existing parameter. A’s concrete `People` alias still refers to its original association.

The list override is different. If A’s published `Page` has already fixed its list representation, B cannot change that internal family merely by changing the element argument. Reuse requires an explicitly exported representation parameter or other supported abstraction point. Otherwise B must publish a distinct declaration under its own configuration, or generation must fail.

Compatibility is therefore **relative to the imported declaration’s dependencies**, not necessarily equality of an entire global configuration.

### Prefer a generated consumer interface for incompatible combinations

For the initial cross-package story, I recommend a consumer-owned generated interface that:

1. Imports the canonical declarations and applicable checked source facts.
2. Selects the consumer’s associations.
3. Owns the resulting configuration-specific evidence and admission declarations.
4. Reuses imported payload families where their published contracts permit it.

This avoids reopening an imported header and does not require a runtime registry.

It also gives an honest treatment of sealing:

- A Go package cannot automatically issue another package’s private nominal evidence.
- A sealed Rust trait also excludes an independently generated downstream implementation.
- A public C++ specialization surface cannot distinguish generated declarations from handwritten grants.

Normal source analysis and generation should produce the new facts. Handwritten semantic grants need not become part of the user workflow.

The minimum composition record is a set of explicit source references, native symbol references, association dependencies, and supported substitution points. A universal digest or new provenance subsystem is unnecessary. Matching names or plugin IDs alone is insufficient.

## 6. Obligations for the agnostic generation protocol

The companion protocol should transport these laws without interpreting kinds.

### A. Preserve complete judgments

The semantic unit is the sequent:

\[
\Gamma \vdash S:K,
\]

including the actual binder identities in \(\Gamma\). Exporting only the conclusion loses the conditions under which it is true.

The supplied exporter already retains assumptions. That is necessary information, but it is not itself a native enforcement mechanism.

### B. Preserve substitution and open/concrete coherence

For every represented substitution \(\sigma\):

\[
\operatorname{Lower}_c(F[\sigma])
\equiv_{\mathrm{API}}
\operatorname{Apply}\bigl(
  \operatorname{Publish}_c(F),
  \operatorname{Expand}_c(\sigma)
\bigr).
\]

The profile defines \(\equiv_{\mathrm{API}}\): native alias identity, the same nominal wrapper application, or another explicitly selected relation.

`Expand` may include a source witness, native type, configuration handle, and several evidence obligations. The law must cover all of them.

`Define` must establish the same equation under fresh formals. It cannot accidentally capture a concrete caller’s certificate and use it as a theorem about all arguments.

### C. Make association independent of the proof route

For one selected configuration, changing which membership theorem is used must not change the payload:

\[
R_c(S\mid\text{proof of }K_1)
=
R_c(S\mid\text{proof of }K_2)
=
R_c(S).
\]

Two native membership traits that independently choose `Repr` violate this law unless their equality is separately enforced.

### D. Preserve obligations before erasure

Argument contracts survive ignored arguments and alias reduction.

`Ignore<wire<text>>` is invalid because its argument contract fails. A proof that the result `text` belongs to Tree cannot repair that application.

Result guarantees are separate. When a profile promises generic composition, result evidence must remain available along that composition path. If the payload alias erases source identity, a separate result descriptor may be needed; the protocol must not reconstruct the theorem from the payload.

### E. Preserve source validity of constructors

A native generic header is not a substitute for Horos’s constructor judgment.

For `F : A -> B`, preserve the original-domain check and the result proof under fresh rigid assumptions. A narrower query cannot rehabilitate an invalid declaration. Abstract constructors expose only their established guarantees.

Deferring native higher-order arguments is reasonable. It must be an explicit unsupported boundary, without weakening ordinary proper-parameter contracts.

### What these laws require of the examples

| Example | Required semantic behavior |
|---|---|
| `Page<T>` | Retain its unconstrained proper-parameter domain. Additional checked implications do not impose a new Data restriction. |
| `DataPage<D>` | Require `D : Data`; make the result’s Data guarantee available under that premise. |
| `TreePage<T>` | Require `T : Tree`; retain the result guarantee for the complete Page body, including optional `next`. |
| `TreePage<Person>` | Use Person’s established membership and the current configuration’s Person association. |
| `TreePage<list<Person>>` | Apply a checked list implication with its prerequisites intact. |
| `Ignore<T>` | Check the input contract even when representation reduction erases the argument. |
| `Page<Cell<Person>>` | Use Cell’s selected mapping without inventing a Data obligation. |
| `DataPage<Cell<Person>>` with Wire inside Cell | Reject from the source judgment, regardless of the selected payload representation. |
| Renamed Tree import | Preserve the resolved identity and judgment without a name-sensitive branch. |
| Global list-family override | Use the same selected family in the open declaration and every represented application. |

These are source-provider obligations carried through opaque facts and handles. The generic coordinator need not recognize Data, Tree, Cell, or any other semantic name.

## 7. What I would change before implementation

### Treat witness types as an encoding choice

The deeper abstraction is a **checked source application with a selected association**. Some targets can expose that through descriptor projections; others need explicit tuples; some useful profiles need only generated names.

Making every application take public source/native/proof parameters prematurely commits the protocol to a difficult proof language. TypeScript bottom, Go inference, Rust trait objects, and C++ specialization show that type-only certificate admission needs more than “a value could not be constructed.”

### Start with a narrow representation domain, without privileging particular kinds

Use the implemented representation slice as the starting point: text, bool, lists, named closed records, optional fields, and supported ordinary proper generics, plus explicitly supported library mappings.

The source membership queries can still concern ordinary imported kinds, including recursive kinds. Restrict the represented expressions and native composition operations rather than adding special cases for familiar kind names.

Unused proper parameters, recursive native declarations, residual constructors, open records, and other currently unsupported representations remain explicit failures until their capabilities are added. The `Ignore` analysis establishes a required law; it does not imply that the present generator already supports it.

### Stage the work in this order

1. **Specify profiles and checking points.** State argument grammar, consumer operations, trust assumptions, identity behavior, and completeness domain.
2. **Establish named applications across targets.** Preserve the existing representation profile and reject requests for unavailable open enforcement.
3. **Evaluate bounded native gates separately.** TypeScript finite selection; Go a genuinely restricted issued-tuple relation; Rust sealed membership with wrapper or projection behavior; C++20 constrained aliases over controlled descriptors.
4. **Add checked theorem families.** Each family must transport its premises and a coherent representation equation. A finite list is not an unbounded family.
5. **Add package composition through explicit dependency contracts.** Use consumer-owned generation when imported associations or headers are incompatible.
6. **Extend recursive representations independently.** Reuse concrete source certificates where possible; do not turn target recursion into an implicit Horos checker.

### Use the counterexamples as acceptance criteria

Before selecting an encoding, write down the required outcome for at least these cases:

| Challenge | Required outcome |
|---|---|
| TypeScript proof parameter `never` | Must not authorize an unrelated inhabited payload under an enforcing claim |
| TypeScript widening or witness unions | Preserve the source/representation correlation and declared choice semantics |
| Go singleton-constraint inference | Must not manufacture authorization for an unissued tuple |
| Go same-underlying-type tokens | Preserve distinct source and argument identities |
| Rust unused alias and constant-output projection | Match the advertised checking point; retain ignored-input obligations when demanded |
| Rust unsized evidence | Do not confuse a nameable trait object with an issued concrete fact |
| C++ positive specialization or late certificate visibility | Follow the declared customization and compilation contract |
| Person override | Reuse source membership while replacing incompatible association evidence |
| List-family override | Preserve open/concrete representation coherence |
| Exhausted analysis or unsupported representation | Fail explicitly rather than erase, guess, or reinterpret |

The most useful common guarantee is therefore:

> Generation transports established source judgments and their assumptions into a target-specific admission mechanism, tied to one selected representation configuration. The profile states when admission is checked, whether identity survives afterward, and how separately generated declarations may compose.

That is a substantial and defensible goal. It preserves the ownership decisions in the brief while avoiding the stronger—and currently unsupported—claim that a uniform native witness API can enforce all Horos kind constraints against unrestricted native consumers.
