# bittype/ACX-004 — Generation emits file syntax before placement

**TypeScript corrected on 8 November 2026. The C++, Rust and Go cases remain open.** The [generation/Files decision](../source.md#from-generated-declarations-to-files)
assigns concrete import and export syntax to the language's Files formatter.

**Original behavior, 7 November.** The Cell mapping correctly requests the public type
`@bitspark/cell` exports as `Cell`. The [TypeScript target](https://github.com/Bitspark/bittype/blob/dbb7ff2/transform/syntax/typescript/target/go/builder.go)
then calls `imports.Emit` while assembling the logical AST, allocating a local
import binding before the consumer has placed a declaration. Its
[declaration builder](https://github.com/Bitspark/bittype/blob/dbb7ff2/transform/syntax/typescript/target/go/symbols.go)
also marks each reserved interface or alias `exported: true`. Later, the
[Files formatter](../../format/files/typescript/provider/go/relocate.go)
discards the old imports, allocates bindings per output unit and consults
export visibility when a use crosses units. The logical unit's syntax is
doing double duty as the record of which dependency was intended.

The same distinction applies outside TypeScript. The [C++ target](https://github.com/Bitspark/bittype/blob/dbb7ff2/transform/syntax/cpp/target/go/assemble.go)
materializes registered headers as include nodes during declaration assembly;
knowing the required public header is distinct from placing its directive in
an output unit. The [Rust target](https://github.com/Bitspark/bittype/blob/dbb7ff2/transform/syntax/rust/target/go/symbols.go)
sets module visibility to public on its reserved structs and aliases. These
are further instances to address, not evidence that native Files placement
has been implemented for those targets.

**Rules.** [AC-02](https://github.com/Bitspark/platform/blob/main/docs/concepts/architectural-correctness.md#ac-02)
assigns representation choice to the mapping and concrete module spelling to
Files. One local alias or export modifier is a decision about a module, not a
property of the type being generated. [AC-06](https://github.com/Bitspark/platform/blob/main/docs/concepts/architectural-correctness.md#ac-06)
applies because generating a single convenient TypeScript module made its
organization a prerequisite for later placements. The successful
[split and co-located examples](../../integration/go/typescript_placement_test.go)
qualify the final imports; they do not establish that the two stages own
different decisions.

**Required correction and qualification.** Preserve each use's target and
publication intent through target semantic admission without using a synthetic
module import or export flag to convey them. Apply one consumer placement in
Files. Generate `Cells = Page<Cell<Person>>` once, then format it twice:
moving `Person` into the file containing `Cells` must remove only the relative
import. Both outputs must preserve bindings and intended visibility, including
in the presence of a conflicting local name; an inaccessible target must fail
instead of being rebound or silently exported. The [planner](../generation-planner.md#where-the-plan-stops)
describes this qualification.

**Implemented TypeScript correction.** Generation retains exposed sites and emitted external use occurrences. Files allocates imports and aliases after placement and checks the compiler's named exports and each relocated destination. The qualification uses one output with a local Cell and an external use of Cell. With Person in a second unit, the relative import is present. Moving Person alongside Page removes its relative import and retains the package import with the alias `Cell_1`. Missing or inaccessible destinations fail publication. [Output](../../contracts/generation/go/output.go) · [Generated Files input](../../format/files/typescript/provider/go/generated.go) · [Placement tests](../../integration/go/typescript_placement_test.go)

**Further instances identified on 10 November 2026. Pending; no correction is implemented.** The [Go target](https://github.com/Bitspark/bittype/blob/33a3287/transform/syntax/golang/target/go/provider.go#L79) writes one package clause, taken from target configuration, on the single file node it constructs. The [C++ target](https://github.com/Bitspark/bittype/blob/33a3287/transform/syntax/cpp/target/go/provider.go#L159) wraps every declaration in one configured namespace. The [placement proposal](../native-file-placement.md#required-checks-before-claiming-support) takes the native scope of each emitted declaration from the consumer's placement. It requires one generated output to be placed both across packages or namespaces and co-located. That is impossible while generation fixes a single package or namespace, and a Files stage that overwrote it would repeat the double duty described above. These are the same AC-02 and AC-06 failures as the import and visibility cases. [Kernel composition](../kernel-composition.md) documents Package and Namespace as target configuration; that describes the present behaviour, not the corrected ownership. **Required correction:** generation carries no package or namespace choice, and Go Files and C++ Files read it from placement. Tracked in [#161](https://github.com/Bitspark/bittype/issues/161) and [#160](https://github.com/Bitspark/bittype/issues/160), which record the decision and its reasons.

**Rust external paths, identified 10 November 2026. Pending.** The [Rust target](https://github.com/Bitspark/bittype/blob/ca5dc80/transform/syntax/rust/target/go/provider.go#L118-L119) spells an external library type as an absolute path inside the declaration and reports no external use. An absolute path stays valid wherever the declaration is placed, so no placement is broken today. The [placement proposal](../native-file-placement.md#rust) nevertheless assigns the import of an external type to Rust Files, and the generated output records no intent that Files could check. Tracked in [#159](https://github.com/Bitspark/bittype/issues/159).

The table below deferred the Rust paths until "the first item of #170 supplies another crate's semantics". That reason does not hold: all three paths name the standard library of the pinned compiler, and recording the use needs no other crate's semantics. A hosted probe established that the Rust helper binds every segment of such a path (run [43362840273](https://github.com/Bitspark/bittype/actions/runs/43362840273), recorded on [#278](https://github.com/Bitspark/bittype/issues/278#issuecomment-6845046456)). **Rules.** [AC-02](https://github.com/Bitspark/platform/blob/main/docs/concepts/architectural-correctness.md#ac-02): which type a use means is generation's statement, and it was carried only by a spelling that the Files stage of the language would have to read back. [AC-10](https://github.com/Bitspark/platform/blob/main/docs/concepts/architectural-correctness.md#ac-10): what an output records about intent may not change after a first slice, so an output that gained its destinations in a later slice would break what the first one delivered. **Delivered with [#276](https://github.com/Bitspark/bittype/issues/276):** the Go target records a Go-issued predeclared symbol at every `string` and `bool`. The Rust target records a Rust-issued symbol on the segment that names the item of each of the three paths, with the crate separate from the path, and at `bool`. The generated text is unchanged. [Destinations](../destinations.md) specifies which nodes are name uses, what a symbol identifies and what counts as the same destination, and a [test per target](../../integration/go/destinations_test.go) asserts that every name use of a sealed TypeScript, Go and Rust output carries exactly one of a reference and an external use. **Still open:** the Rust target still writes the absolute path, so generation still decides the qualification. Slice 1 of [#159](https://github.com/Bitspark/bittype/issues/159) makes the fragment write one segment that carries the symbol, and Rust Files writes the path. Nothing compares a use with its destination in Go or Rust until the Files formatters of slice 1 of [#161](https://github.com/Bitspark/bittype/issues/161) and of #159 exist. The Rust helper publishes no binding for `bool`, so Rust Files cannot establish that destination before the helper does. A crate of a library stays with [#170](https://github.com/Bitspark/bittype/issues/170), and a Go package of a library with slice 2 of #161. **C++ records no destination**, for `::std::string`, `::std::vector`, the external form, the namespace segment or the includes, until [#160](https://github.com/Bitspark/bittype/issues/160): row 36 of research 0016 excludes legacy C++ output.

**Go names, recorded 13 November 2026. Pending; no correction is implemented.** The evaluation of [research 0016](../../research-docs/0016-native-files-placement.md) found this instance on 12 November 2026 (row 13 of its table), and the case did not list it. In Go the case of the first letter of a package-level name is its visibility to other packages. Generation decides that case for every Go declaration. The [shared naming function](https://github.com/Bitspark/bittype/blob/9961adb/transform/syntax/horos/mapping/naming/go/naming.go#L25-L26) capitalizes the first letter. The [declaration recipe](https://github.com/Bitspark/bittype/blob/9961adb/transform/syntax/horos/mapping/declarations/go/declarations.go#L41), which all four targets share, applies it to every declaration, and the [Go target](https://github.com/Bitspark/bittype/blob/9961adb/transform/syntax/golang/target/go/provider.go#L76) writes the result on the declaration. The recipe runs before exposure is known: the [planner](https://github.com/Bitspark/bittype/blob/9961adb/contracts/generation/go/planning.go#L182-L190) declares a root and only then marks it exposed. So every generated Go declaration is exported, whether the caller exposed it or not. The name of the [optional helper](https://github.com/Bitspark/bittype/blob/9961adb/transform/syntax/horos-to-golang/mapping/optional/go/optional.go#L24) is a literal, also exported. This is the Go form of the Rust visibility case above. The [generation/Files decision](../source.md#from-generated-declarations-to-files) gives the Files formatter the task "Realize the requested visibility under the language's rules", and in Go that rule is the case of the name. The same shared function holds a second meaning of one language: it turns `Self` into `Self_` for [all four targets](https://github.com/Bitspark/bittype/blob/9961adb/transform/syntax/horos/mapping/naming/go/naming.go#L28-L30), and `Self` is reserved only in Rust ([#268](https://github.com/Bitspark/bittype/issues/268)). **Rules.** [AC-02](https://github.com/Bitspark/platform/blob/main/docs/concepts/architectural-correctness.md#ac-02): the case of a Go name and a reserved word of Rust are meanings of one language each, and a recipe on the horos side that every target shares decides both. Module visibility in Go is realized by Go Files, not chosen during generation. [AC-10](https://github.com/Bitspark/platform/blob/main/docs/concepts/architectural-correctness.md#ac-10): this is a decision in the wrong place and not missing coverage, so it moves first, as its own change. **Required correction:** generation records a naming intent: the mapping's chosen name, the module's identity, the identity of the naming policy that the consumer's composition selected, and the spelling that the policy produced. The mapping spells, and decides no visibility. Go gets its own rule, and it is a check: a spelling is exported when it begins with an upper-case letter, and Go Files refuses a declaration that requires public access and whose spelled intent is not exported, as unsupported coverage. It renames nothing. A requested root requires public access, and so does a declaration whose contribution states that it is part of a public representation, such as the optional helper. The capital that the mapping writes is its style for every target and decides no access. Go Files also checks collisions in the placed package and reports the realized name. It refuses an output with an unexposed source declaration in the public representation of an exposed one as unsupported coverage, and the refusal names every such declaration. Go's unexported spelling is deferred by the [decisions of 13 November 2026](https://github.com/Bitspark/bittype/issues/274#issuecomment-6838436844) on #274, with a trigger: a representation in which an unexposed source declaration is not part of an exposed one's public representation, or a request that can state access beyond its roots. The shared naming function holds no reserved word, and Rust refuses `Self`. The [naming design](../naming.md) of 13 November 2026 records this with its sources. Tracked in [#274](https://github.com/Bitspark/bittype/issues/274) for the intent, Go's check and the reserved word, and in slice 1 of [#161](https://github.com/Bitspark/bittype/issues/161) for its use in Go Files. The text of #161 still expects an unexported spelling for every declaration that is not exposed, which those decisions defer. It stays pending until slice 1 of #161 is verified.

**Order of correction, 11 November 2026. Pending; nothing in this section is implemented.** The owner directed: "if something is placed incorrectly, it is incorrect and must change. Something that is missing can be healed additively, i.e. there is nothing wrong requiring removal." And: "no compromise on architecture, but practical deferral is allowed, if the huge effort justifies it." ([AC-10](https://github.com/Bitspark/platform/blob/main/docs/concepts/architectural-correctness.md#ac-10)). Each open instance is therefore corrected in two steps. The first step moves the misplaced decision to the language's generated-Files formatter, for the placements that existing semantic evidence can check, and refuses every other placement. The second step adds coverage and changes nothing the first delivered. The first step cannot skip its check: [`NewGeneratedFilesFormatter`](../../contracts/format/go/generated.go) refuses a formatter without a preparation step, and since 13 November 2026 ([#273](https://github.com/Bitspark/bittype/issues/273)) the shared formatter refuses each request whose step returns no guard or a requirement without semantic evidence. The requirement belongs to one request, so that refusal moved from construction to the request.

**Why C++ is deferred.** C++ has no resolution or analysis provider, so a C++ generated-Files formatter cannot be constructed under the shared contract. Removing the includes and the namespace without one would leave the generated header unable to compile. Accepting a formatter without semantic evidence would weaken a guarantee the shared mechanism owns. This is a deferral for effort with a stated trigger. It is not an accepted design, and both C++ instances stay open violations.

The C++ header directives and Rust module visibility described above require separate target and Files work. The declarative planner and mapping redesign are implemented; they do not resolve these separate Files ownership cases.
